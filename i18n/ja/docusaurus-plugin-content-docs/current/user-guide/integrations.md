# インテグレーション

インテグレーションは、外部サービスが Semaphore の URL を呼び出したときにタスクテンプレートを開始します。呼び出し元は GitHub、GitLab、Bitbucket、監視システム、あるいは HTTP リクエストを送れる任意のプログラムです。リクエストは実行の引き金になるだけではありません。ブランチ名、コミット、リリースタグといったその一部を、変数としてタスクに渡すこともできます。

![インテグレーションの一覧](/assets/integrations-list.webp)

どのインテグレーションも 4 つの部品でできています。

| 部品 | 答える問い |
|---|---|
| **エイリアス** | 送信側はどの URL を呼ぶのか |
| **認証方式** | このリクエストは何かを開始してよいのか |
| **マッチャー** | *この*リクエストこそインテグレーションが待っていたものか |
| **値の抽出** | リクエストのどのフィールドが、何としてタスクに届くのか |

作成するには、プロジェクトメニューの **Integrations** を開いて **New Integration** をクリックし、名前を付け、実行するタスクテンプレートと認証方式を選びます。続いて一覧でインテグレーションをクリックすると、そのエイリアス、マッチャー、値の抽出を設定できます。

![インテグレーションの詳細](/assets/integration-detail.webp)

## 呼び出しが処理される流れ {#how-a-call-is-handled}

1. 送信側が `/api/integrations/<alias>` を `GET` または `POST` で呼び出します。
2. Semaphore はエイリアスから、開始しうるインテグレーションを特定します。このエンドポイントは公開されており、守っているのはエイリアスと認証方式だけです。
3. 該当する各インテグレーションが、自分の**認証方式**でリクエストを検証します。検証に失敗したリクエストは何も開始しません。
4. 呼び出しが**プロジェクトエイリアス**経由で届いた場合は、インテグレーションの**マッチャー**が評価されます。すべて一致しなければ、そのインテグレーションはスキップされます。
5. **値の抽出**が実行され、リクエストの一部が変数とタスクパラメーターになります。
6. タスクが作成されてキューに入ります。人がテンプレートを手で開始したときとまったく同じです。

処理された呼び出しには、何かが開始されたかどうかに関わらず、本文が空の `204 No Content` が返ります。何が開始されたかはレスポンスヘッダーで示されます。

| レスポンスヘッダー | 値 |
|---|---|
| `X-Semaphore-Task-ID` | 作成されたタスク |
| `X-Semaphore-Template-ID` | それが実行するテンプレート |
| `X-Semaphore-Project-ID` | タスクが属するプロジェクト |
| `X-Semaphore-Integration-ID` | 開始したインテグレーション |
| `X-Semaphore-Inventory-ID` | タスクのインベントリ（ある場合） |

既知のエイリアスへの呼び出しは[呼び出し履歴](#call-history)にも記録されます。Webhook が期待どおりに動かないときに見るべき場所です。

## エイリアス {#aliases}

エイリアスは Webhook URL のランダムで推測できない部分、`/api/integrations/<random_string>` です。`GET` と `POST` を受け付けます。種類は 2 つあり、1 つのインテグレーションが同時に使えるのはどちらか一方です。

**プロジェクトエイリアス**はインテグレーション一覧の上にある **Add Alias** で作成し、**Use project alias** スイッチが入っているプロジェクト内のすべてのインテグレーションで共有されます。届いたリクエストはそれら全部に渡され、各インテグレーションが自分のマッチャーで実行するかどうかを決めます。GitHub や GitLab には一度このエイリアスを渡し、あとはマッチャーでイベントごとに振り分けるのが定石です。

**インテグレーションエイリアス**はインテグレーション自身のページの **Add Alias** で作成し、そのインテグレーション専用になります。呼び出すとただちに開始され、**マッチャーはまったく評価されません**。送信側の用途が 1 つに決まっている場合や、本文がマッチャーでは調べられない形式の場合に使います。

:::warning
どちらの種類のエイリアスが機能するかは、インテグレーションページの **Use project alias** スイッチが決めます。オンの間はインテグレーションがプロジェクトエイリアスに応答し、自分専用のエイリアスは無視されます。オフの間はプロジェクトエイリアスがそのインテグレーションに届かず、マッチャーも一切使われません。
:::

プロジェクトは両方の種類のエイリアスを複数持てます。横のごみ箱アイコンで削除すると即座に使えなくなりますが、すでに受け取った呼び出しは履歴に残ります。

## 認証 {#authentication}

Webhook のエンドポイントはログインの内側にはないため、見知らぬ相手がタスクを開始するのを防ぐのは認証方式です。インテグレーションのフォームで選びます。**Auth secret** は[キーストア](/user-guide/key-store)のキーです。

| 認証方式 | Semaphore が検証する内容 | Auth secret |
|---|---|---|
| **None** | 何も検証しません。URL を知った人は誰でもテンプレートを開始できます | — |
| **GitHub Webhooks** | `X-Hub-Signature-256` が `sha256=` と本文の HMAC-SHA256 の連結に等しいこと | 文字列、またはログイン/パスワードキーのパスワード |
| **Bitbucket Webhooks** | `X-Hub-Signature` を同じ方法で検証 | 文字列、またはログイン/パスワードキーのパスワード |
| **Token** | **Auth header** で指定したヘッダーが秘密と等しいこと | 文字列、またはログイン/パスワードキーのパスワード |
| **HMAC** | **Auth header** で指定したヘッダーが本文の HMAC-SHA256 を含むこと | 文字列、またはログイン/パスワードキーのパスワード |
| **HMAC (SHA-512)** | 同じことを HMAC-SHA512 で | 文字列、またはログイン/パスワードキーのパスワード |
| **BasicAuth** | `Authorization` ヘッダーがログイン*と*パスワードを運ぶこと | ログイン/パスワードキーのみ |

**文字列**キーはその値を共有秘密として使い、ログイン/パスワードキーはそのパスワードを使います。ログインも比較するのは BasicAuth だけです。その方式が使えない種類のキーが設定されている場合、不一致を黙って無視するのではなく、リクエストを拒否します。

### HMAC 認証 {#hmac-authentication}

HMAC 認証方式（`hmac` / SHA-256 と `hmac-sha512` / SHA-512）は、Webhook の本文が共有秘密で署名されていることを検証します。

設定する項目:

1. **Auth header** — 署名を運ぶリクエストヘッダー（例: `X-Signature` や `X-Hub-Signature-256`）。
2. **Auth secret** — キーストアの**文字列**キー（その値が秘密）またはログイン/パスワードの資格情報（その**パスワード**が秘密）。

送信側は、リクエストの生の本文の HMAC ダイジェストを**素の 16 進数**でそのヘッダーに入れる必要があります（`sha256=` / `sha512=` の接頭辞は付けません。GitHub と Bitbucket の方式は逆にその接頭辞を期待し、HMAC 方式は期待しません）。Semaphore は設定された秘密で計算した本文の `HMAC-SHA256` または `HMAC-SHA512` と比較します。

OpenSSL を使った SHA-512 の例:

```bash
SECRET='your-webhook-secret'
BODY='{"event":"deploy"}'
SIG="$(printf '%s' "$BODY" | openssl dgst -sha512 -hmac "$SECRET" | awk '{print $2}')"

curl -X POST "https://semaphore.example.com/api/integrations/<alias>" \
  -H "Content-Type: application/json" \
  -H "X-Signature: ${SIG}" \
  --data "$BODY"
```

## マッチャー {#matchers}

マッチャーは、届いたリクエストに対する 1 つの条件です。*このヘッダーがこの値に等しい*、*この JSON フィールドがこの文字列を含む*、といった形です。1 つのプロジェクトエイリアスで多数のインテグレーションをさばけるのはマッチャーのおかげです。GitHub はすべてのイベントを同じ URL に送るので、どのインテグレーションがどのイベントに反応するかはマッチャーが決めます。

マッチャーが決めるのはインテグレーションを実行するかどうかだけです。タスクを変えることは決してありません。それは値の抽出の役目です。

マッチャーは**プロジェクトエイリアス経由で届いた呼び出しに限って**評価されます（**Use project alias** スイッチがオンのとき）。インテグレーション専用のエイリアスへの呼び出しは、マッチャーを見ずにそのインテグレーションを開始します。

### マッチャーの各項目 {#matcher-fields}

| 項目 | 意味 |
|---|---|
| **Name** | 一覧に表示されるラベル。自由入力で、比較には使われません |
| **Match on** | **Body** か **Header** — 値をどこから取るか |
| **Body Data Format** | **JSON** か **String**。**Body** のときだけ表示されます |
| **Key** | ヘッダー名、または JSON 本文内のフィールドへのパス |
| **Comparison Method** | `==`、`!=`、**Contains** |
| **Value** | リクエストの値と比較されるテキスト |

**Match on: Header** — **Key** はヘッダー名で、大文字小文字は区別されません。`X-GitHub-Event` と `x-github-event` は同じヘッダーです。リクエストに無いヘッダーは「欠けている値」として扱われます（下記参照）。同じヘッダーが複数回現れる場合、比較されるのは最初の値だけです。

**Match on: Body, JSON** — **Key** は解析された本文の中のパスで、次の節で説明します。正しい JSON でない本文は、どのキーに対しても欠けている値を返します。

**Match on: Body, String** — 生の本文全体が値になり、**Key** は無視されます。必須項目なのでフォームはそれでもキーを求めます。ハイフンでも入れておいてください。JSON でない本文を照合できる唯一の方法で、**Contains** と組み合わせて使います。

**Key** と **Value** はどちらも必須なので、マッチャーで空の値を調べることはできません。フィールドが無いことに反応させたい場合は、そのフィールドが決して取らない値と `!=` で比較します。

### JSON のキー {#json-keys}

キーは JSON 文書をたどるパスです。階層はドットで区切り、配列の要素は 0 から数えた添字を角かっこで指定します。名前の大文字小文字は区別されます。

```json
{
  "ref": "refs/heads/main",
  "repository": { "name": "semaphore", "private": false },
  "commits": [
    { "id": "9fceb02", "message": "Fix the deploy" },
    { "id": "1c4a7b8", "message": "Bump the version" }
  ]
}
```

| キー | 指す値 |
|---|---|
| `ref` | `refs/heads/main` |
| `repository.name` | `semaphore` |
| `repository.private` | `false` |
| `commits.[0].id` | `9fceb02` |
| `commits.[1].message` | `Bump the version` |
| `commits` | 配列全体 |
| `repository.url` | 何も指しません（そのフィールドは存在しません） |

値の抽出の **Key** 欄も同じ構文を使います。

### マッチャーによる値の比較 {#how-a-matcher-compares-values}

リクエストから取った値はテキストに変換され、**Value** とテキストとして比較されます。そのため **Value** 欄に引用符や角かっこ、エスケープを書く必要はありません。

- **文字列**はそのまま比較され、大文字小文字も区別されます。`Push` は `push` に一致しません。
- **数値**は小数部が無い場合、小数部なしで比較されます。本文の `42` は値 `42` に一致し、`42.0` には一致しません。小数のある数値は書かれたまま比較されるので、`1.5` は `1.5` に一致します。
- **真偽値**は `true` と `false` に一致します。
- **欠けている値**（ヘッダーが無い、JSON のパスが存在しない、`null`、正しい JSON でない本文）は、リテラルのテキスト `<nil>` として比較されます。ここから覚えておくべき帰結が出てきます。欠けているフィールドに `==` が一致することは決してなく、`!=` は必ず一致します。
- **オブジェクトと配列**には読めるテキスト表現がないので、比較しないでください。代わりに、その中のスカラー値のフィールドをキーで指してください。
- **Contains** は大文字小文字を区別する単純な部分文字列判定で、ワイルドカードも正規表現もありません。

### 複数のマッチャー {#several-matchers}

インテグレーションはマッチャーをいくつでも持てます。それらは **AND** で結合され、すべてが一致したときにだけインテグレーションが実行されます。1 つのインテグレーションの中で*または*を表す方法はありません。別の条件には、同じテンプレートに対する 2 つめのインテグレーションを作ってください。

:::warning
プロジェクトエイリアスを使い、**マッチャーを 1 つも持たない**インテグレーションは決して開始されません。一致しうるものが何も無いからです。少なくとも 1 つマッチャーを与えるか、**Use project alias** をオフにしてインテグレーション専用のエイリアスを呼び出してください。
:::

### マッチャーの例 {#matcher-examples}

| 目的 | Match on | 形式 | Key | メソッド | Value |
|---|---|---|---|---|---|
| GitHub の push だけ | Header | — | `X-GitHub-Event` | `==` | `push` |
| `main` への push だけ | Body | JSON | `ref` | `==` | `refs/heads/main` |
| `main` 以外のブランチ | Body | JSON | `ref` | `!=` | `refs/heads/main` |
| タグだけ | Body | JSON | `ref` | Contains | `refs/tags/` |
| マージ済みの GitLab マージリクエストだけ | Body | JSON | `object_attributes.state` | `==` | `merged` |
| ボットのコミットを無視する | Body | JSON | `pusher.name` | `!=` | `dependabot` |
| 公開済みの GitHub リリースだけ | Body | JSON | `action` | `==` | `published` |
| ディスクに触れたプレーンテキストの警報 | Body | String | `-` | Contains | `disk` |

最初の 2 行を組み合わせたものが、デプロイ用インテグレーションの定番設定です。イベント種別はヘッダーから、ブランチは本文から取り、どちらも一致しなければなりません。

## 値の抽出 {#value-extractors}

値の抽出は、届いたリクエストの一部を、これから始まるタスクへコピーします。Webhook がブランチ、コミットハッシュ、作者、リリース版数などを、起動する自動化処理へ渡す仕組みです。

抽出はどの種類のエイリアス経由で呼び出しが来ても必ず実行され、認証とマッチャーを通過したあとに行われます。

### 抽出の各項目 {#extractor-fields}

| 項目 | 意味 |
|---|---|
| **Name** | 一覧に表示されるラベル。自由入力 |
| **Source of the Value** | **Body** か **Header** |
| **Data Type of Body** | **JSON** か **String**。**Body** のときだけ表示されます |
| **Key** | ヘッダー名、または [JSON のキー](#json-keys)。マッチャーと同じ構文です |
| **Variable Usage** | **Variables** か **Task Params** — 値をどこへ渡すか |
| **Variable** | タスクの中で値が持つ名前 |

**Body** と **String** の組み合わせでは、マッチャーとまったく同じように生の本文全体が値になり、**Key** は無視されます。

### 変数が受け取るもの {#what-the-variable-receives}

マッチャーと違い、抽出は何もテキストに変換しません。JSON の値は型を保つので、数値は数値のまま、オブジェクトはオブジェクトのままです。

| リクエストにあるもの | 変数が受け取るもの |
|---|---|
| ヘッダー | そのテキスト。ヘッダーが無い場合は空文字列 |
| JSON の文字列・数値・真偽値 | 同じ値と、その型 |
| JSON のオブジェクトや配列 | 構造を保ったオブジェクトまたは配列の全体 |
| JSON の `null`、存在しないパス、正しい JSON でない本文 | 何も受け取りません。変数は**まったく設定されず**、テンプレートが定めた値がそのまま残ります |
| **String** としての本文 | 生の本文全体のテキスト |

「空」と「未設定」の違いは重要です。ヘッダーが無い場合はタスクに空文字列が渡りますが、JSON のフィールドが無い場合はテンプレート自身の値がそのまま使われます。

### Variable Usage: Variables {#variable-usage-variables}

値はタスクの変数に加わります。新規タスクのダイアログの **Variables** 欄が埋めるものと同じ集合です。Semaphore はこれらを追加変数としてツールに渡し（Ansible なら `--extra-vars`、Terraform なら `-var`）、テンプレートの[変数グループ](/user-guide/environment)にある同名のキーを上書きします。

変数名をテンプレートの[サーベイ変数](/user-guide/task-templates/survey-vars)とまったく同じにすれば、人が入力する代わりに Webhook がそのサーベイ変数を埋めます。

### Variable Usage: Task Params {#variable-usage-task-params}

タスクパラメーターは、Playbook 向けの変数ではなく、テンプレートに組み込まれた[プロンプト](/user-guide/task-templates/prompts)です。抽出した値はそのまま渡されるので、JSON の型が期待どおりでなければなりません。`"true"` ではなく `true` です。

| 変数 | 対象 | 期待する型 |
|---|---|---|
| `git_branch` | すべてのアプリ | チェックアウトするブランチ。先頭の `refs/heads/` は取り除かれるので、GitHub の `ref` をそのまま使えます |
| `limit`、`tags`、`skip_tags` | Ansible | 文字列のリスト |
| `debug`、`dry_run`、`diff` | Ansible | `true` または `false` |
| `plan`、`destroy`、`auto_approve`、`upgrade`、`reconfigure` | Terraform、OpenTofu、Terragrunt | `true` または `false` |

値が効くには、テンプレート側で上書きを許可しておく必要があります。`git_branch` には **Allow override branch in task**、`limit`、`tags`、`skip_tags` には対応するプロンプトです。許可が無ければ値は捨てられ、タスクはテンプレートの設定で実行されます。

### 抽出の例: GitHub の push {#extractor-example-github-push}

GitHub の push Webhook は、次のように始まる本文を送ります。

```json
{
  "ref": "refs/heads/main",
  "after": "9fceb02d0ae598e95dc970b74767f19372d61af8",
  "repository": { "name": "semaphore", "default_branch": "main" },
  "pusher": { "name": "octocat", "email": "octocat@example.com" }
}
```

4 つの抽出で、これを十分に説明されたタスクに変えられます。

| Name | Source | 形式 | Key | Usage | Variable |
|---|---|---|---|---|---|
| Branch | Body | JSON | `ref` | Task Params | `git_branch` |
| Commit | Body | JSON | `after` | Variables | `COMMIT` |
| Author | Body | JSON | `pusher.name` | Variables | `AUTHOR` |
| Event | Header | — | `X-GitHub-Event` | Variables | `EVENT` |

するとタスクは `main` をチェックアウトし（`refs/heads/` の接頭辞は自動で取り除かれます）、Playbook から使える変数 `COMMIT`、`AUTHOR`、`EVENT` とともに実行されます。実際の呼び出しが何を届けたのかを確かめるには、History タブでその呼び出しを開き、本文と自分のキーを見比べてください。

## 既定のタスクパラメーター {#task-parameters}

インテグレーションのフォームでテンプレートを選ぶと、そのテンプレート自身の実行オプションが現れます。メッセージ、サーベイ変数、インベントリ、テンプレートが上書きを許していればGit ブランチ、そしてアプリのプロンプトです。ここで設定した内容は、このインテグレーションが開始するすべてのタスクの既定値になります。インベントリや固定のメッセージのように決して変わらない値は、抽出ではなくここに書いてください。

抽出はこの既定値の上に適用されます。抽出が生んだ変数やタスクパラメーターは同名の既定値を置き換え、抽出が何も見つけられなかったときは既定値がそのまま残ります。

## ワークフローのインテグレーション <FeatureState feature="workflows" /> {#workflow-integrations}

インテグレーションは 1 つのテンプレートの代わりに[ワークフロー](/user-guide/workflows)を開始することもできます。インテグレーションのフォームで **Runs** を **Workflow** に切り替え、ワークフローを選んでください。

抽出の動きは同じですが、1 点だけ違います。**Variable Usage** は無視され、抽出されたすべての値が **Variable** の名前でワークフローのサーベイへの回答として渡されます。ワークフローはその回答を検証し、各ノードのバインディングを通して届けるので、どのノードにもバインドされていない値はタスクに届きません。成功した呼び出しは、タスクのヘッダーに加えて `X-Semaphore-Workflow-ID` と `X-Semaphore-Workflow-Run-ID` を返します。

## 呼び出し履歴 {#call-history}

インテグレーションページの **History** タブには、プロジェクトがいずれかのエイリアスで受け取ったすべての呼び出しが新しい順に並びます。インテグレーション単位ではなくプロジェクト単位で保持されるため、エイリアス、インテグレーション、開始したタスクが無くなっても履歴は残ります。

| 列 | 表示される内容 |
|---|---|
| **Time** | 呼び出しが届いた時刻 |
| **Integration** | 処理したインテグレーションと、その下にエイリアス（エイリアスをクリックすると一覧をそれで絞り込めます） |
| **Source IP** | 呼び出し元のアドレス |
| **Method** | `GET` または `POST` |
| **Status** | インテグレーションがその呼び出しをどう扱ったか、そしてその理由 |
| **Task** | 開始したタスクまたはワークフロー実行 |
| **Duration** | インテグレーションが呼び出しの処理に要した時間 |

状態は 4 種類あります。

| 状態 | 意味 |
|---|---|
| `ok` | タスクまたはワークフロー実行が開始しました |
| `unauthorized` | リクエストがインテグレーションの認証方式を通りませんでした |
| `skipped` | マッチャーが一致しなかった、またはそのエイリアスがどのインテグレーションも開始しませんでした |
| `error` | 開始を試みて失敗しました（テンプレートが無い、サーベイが値を受け付けないなど） |

行をクリックすると、受け取ったままのリクエスト本文（先頭 64 KiB まで。それより長かった場合は保存されたサイズと元のサイズの両方が表示されます）を含めて呼び出しが開きます。リクエストの**ヘッダーは一切保存されません**。送信側が認証に使った署名やトークンを運んでいるからです。認証を通らなかった呼び出しの本文も保存されません。URL を知っていれば誰でも送れるものだからです。

表の上のコントロールでインテグレーションとエイリアスで絞り込み、下の矢印でページを移動します。履歴に保存期限はなく、プロジェクトが削除されるまで増え続けます。

## トラブルシューティング {#troubleshooting}

| 症状 | 確認すること |
|---|---|
| History に行がまったく現れない | URL のエイリアスが間違っているか削除されています。**Use project alias** がオンのときにインテグレーション専用エイリアスを呼んだ場合も、どこにも記録されません |
| `unauthorized` | 認証ヘッダーの名前、キーストアのキー、そして送信側が方式の期待する `sha256=` 接頭辞付きで署名を送っているか。GitHub と Bitbucket は **Auth header** に関係なく独自のヘッダーを使います |
| `skipped`、理由が *No integration matched the alias* | エイリアスは存在するが、プロジェクト内のどのインテグレーションも **Use project alias** をオンにしていません |
| `skipped`、理由が *No matcher matched the request* | 呼び出しを開き、本文を自分のマッチャーと見比べてください。欠けているフィールドは `==` に決して一致せず、キーは大文字小文字を区別し、**Contains** にワイルドカードは無いことを思い出してください。マッチャーが 1 つも無いインテグレーションも同じ理由でスキップされます |
| タスクは走るが変数が空、または存在しない | JSON のキーがペイロードと合っていない（呼び出しを開いて本文を確認）、値が `null` だった、あるいは **Variable** の名前が埋めたいサーベイ変数と違っています |
| ブランチが上書きされない | テンプレートに **Allow override branch in task** が必要で、抽出は `git_branch` タスクパラメーターに書き込む必要があります |
| 1 回の呼び出しで複数のタスクが始まる | 複数のインテグレーションがプロジェクトエイリアスを使い、そのマッチャーがすべて一致しています。マッチャーを絞るか、各インテグレーションに専用のエイリアスを与えてください |
