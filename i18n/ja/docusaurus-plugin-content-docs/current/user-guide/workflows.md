# ワークフロー <Pro />

ワークフローを使うと、複数のタスクテンプレートを分岐、承認、時間待ちを含む有向グラフ (DAG)
として連結できます。ワークフローの実行は各ステップの完了に合わせて自動的に進みます。グラフは
ビジュアルエディターで一度設計し、その後はワークフローのページから実行を開始します。

:::info
ワークフローは **Semaphore Pro** の機能です。ワークフローのメニュー項目は、サブスクリプションに
含まれている場合にのみ表示されます。
:::

## 概要 {#overview}

ワークフローは次の要素で構成されます。

- **ノード** — グラフ内のステップです（テンプレートの実行、承認の待機、一定時間の待機、
  メモによる注記）。
- **エッジ** — ノード間の接続です。それぞれに **条件** のラベルが付き、後続のノードを
  いつ開始するかを制御します。

ワークフローを開始すると、Semaphore は **ワークフローの実行** を作成します。進行はサーバーが
制御します。タスクが完了し、承認が解決され、待機時間が経過するたびに、エッジの条件に従って
後続のノードが開始されます。

## ワークフローの作成 {#creating-a-workflow}

1. プロジェクトを開き、**ワークフロー** に移動します。
2. **新しいワークフロー** をクリックします。
3. グラフィカルエディターで次の操作を行います。
   - パレットからキャンバスにノードをドラッグします。
   - あるノードの出力ハンドルから別のノードへドラッグして、ノードを接続します。
   - ノードまたはエッジをクリックすると、サイドパネルでそのプロパティを編集できます。
4. **名前** を設定します（必要に応じて、実行のバージョン管理用に **開始バージョン** も設定します）。
5. **問題** パネルに表示されている問題を解消し、**保存** をクリックします。

![ワークフローのエディター](/assets/workflow-editor.webp)

エディターは保存前にグラフを検証します。有効なワークフローには、少なくとも 1 つのノードがあり、
開始ノードがちょうど 1 つ（入力エッジを持たないノード）あり、循環がなく、実行可能なすべての
ノードの構成が完了している必要があります。

## ノードの種類 {#node-kinds}

| 種類 | 目的 |
|------|---------|
| **タスク** | タスクテンプレートを実行します。**タスクパラメーター** により、ノードごとにテンプレートのパラメーター（インベントリ、変数グループ、Ansible の limit、追加の CLI 引数）を上書きできます。 |
| **承認** | 権限を持つユーザーが承認または却下するまで、実行を一時停止します。必要に応じてタイムアウト（秒）と承認メッセージを設定できます。 |
| **待機** | 設定した秒数だけ待ってから、後続のノードに進みます。冷却期間、メンテナンスウィンドウ、依存するステップの間隔調整などに便利です。 |
| **メモ** | キャンバス上の自由形式の注記です。メモのノードは実行されず、エッジで接続されることもありません。ドキュメント用の要素です。 |

### 合流 {#convergence}

複数の入力エッジを持つノードは、上流のノードの **すべて** の完了を必要とするか（既定）、
**いずれか** 1 つの完了で進むかを指定できます。ノードのプロパティパネルで **合流** を設定します。

### 待機ノード {#delay-nodes}

待機ノードは、設定した時間（最短 1 秒）だけワークフローの実行を一時停止します。待機中は
次のようになります。

- 実行は **running** のステータスのままです。
- 実行のビューでは、待機ノードにカウントダウンがリアルタイムで表示されます。
- エッジで接続された後続のノードは、待機が完了するまで開始されません。

待機が有効な間にワークフローの実行が **停止** された場合、待機はキャンセルされ、実行は
**stopped** のステータスで終了します。

### 承認ノード {#approval-nodes}

実行が承認ノードに到達すると、誰かが承認または却下するまでステータスが **approval** に
変わります。実行のビューに承認／却下の操作が表示されます。却下された承認は、接続されている
エッジの条件に従って実行を失敗させます。

## エッジの条件 {#edge-conditions}

各エッジには、後続のノードがいつ実行可能になるかを決める条件があります。

| 条件 | 上流のノードが次の状態になったときに後続が開始します |
|-----------|-------------------------------------------|
| **成功時** | 正常に完了したとき（既定）。 |
| **失敗時** | エラーで完了したとき。 |
| **常に** | 終了状態（成功または失敗）のいずれかで完了したとき。 |

**失敗時** の分岐は、補償処理や通知に使用します。結果に関係なく次のステップを実行する場合は
**常に** を使用します。

## 実行と監視 {#running-and-monitoring}

- **ワークフローを実行** — ワークフローの一覧から新しい実行を開始します。
- **実行のビュー** — 各ノードのステータス（実行中、成功、失敗、承認、待機のカウントダウン）を
  リアルタイムで表示する全画面のグラフです。
- **停止** — 実行が `running` または `approval` の間、`run_project_tasks` を持つユーザーは
  実行を停止できます。実行中のすべてのタスクが停止され、保留中の承認は却下され、実行は
  **stopped** としてマークされます。

実行のステータス: `running`、`approval`、`success`、`failed`、`stopped`。

## 実行のバージョン管理 {#run-versioning}

ワークフローに **開始バージョン**（たとえば `1.0.0`）を設定すると、各実行にバージョンの
ラベルが付きます。Semaphore はビルドテンプレートと同様に、実行ごとにバージョンを増加させます。

## ワークフローのアーティファクト（set_stats） {#workflow-artifacts-set_stats}

ワークフロー内の Ansible のタスクが `set_stats` を使用すると、その変数はその実行の
**ワークフローのアーティファクト** として保存されます。同じ実行内の後続のタスクノードは、
それらを追加の変数として自動的に受け取ります。

:::warning
ワークフローのステップが **リモートのランナー** で実行される場合、ワークフローのアーティファクトは
まだリモートランナーのステップ間では受け渡されません。受け渡されるのは、Semaphore サーバー上で
ローカルに実行されたタスクの間のみです。アーティファクトの受け渡しを計画する際はこの点を考慮するか、
アーティファクトを生成するステップと利用するステップを同じ実行経路に配置してください。
:::

## 権限 {#permissions}

- ワークフローの管理（作成、編集、削除）には、プロジェクトのリソース管理の権限が必要です。
- ワークフローの実行には `run_project_tasks` が必要です。
- 承認の解決には、適切なプロジェクトのアクセス権が必要です（そのプロジェクトでタスクを
  実行できるユーザーと同じです）。

## API {#api}

ワークフローのテンプレートと実行は
`/api/project/{project_id}/workflows` で利用できます。リクエストとレスポンスのスキーマ
（`delay` ノードのフィールド（`delay_seconds`）や停止のエンドポイント
（`POST …/runs/{run_id}/stop`）を含む）については、[API ドキュメント](/reference/api)を
参照してください。
