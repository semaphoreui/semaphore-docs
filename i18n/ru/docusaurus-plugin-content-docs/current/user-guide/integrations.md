# Интеграции

Интеграция запускает шаблон задачи, когда внешний сервис обращается к URL Semaphore. Вызывающей стороной может быть GitHub, GitLab, Bitbucket, система мониторинга или любая программа, умеющая отправлять HTTP-запросы. Запрос не только запускает выполнение: его части — имя ветки, коммит, тег релиза — могут быть переданы в задачу как переменные.

![Список интеграций](/assets/integrations-list.webp)

У каждой интеграции есть четыре составные части:

| Часть | Отвечает на вопрос |
|---|---|
| **Алиас** | По какому URL обращается отправитель? |
| **Способ аутентификации** | Разрешено ли этому запросу что-либо запускать? |
| **Сопоставители** | Тот ли это запрос, которого ждёт интеграция? |
| **Извлечение значений** | Какие поля запроса попадут в задачу и в каком виде? |

Чтобы создать интеграцию, откройте раздел **Integrations** в меню проекта и нажмите **New Integration**: задайте имя, выберите шаблон задачи, который она запускает, и способ аутентификации. Затем щёлкните по интеграции в списке, чтобы настроить её алиас, сопоставители и извлечение значений.

![Подробности интеграции](/assets/integration-detail.webp)

## Как обрабатывается вызов {#how-a-call-is-handled}

1. Отправитель обращается к `/api/integrations/<alias>` методом `GET` или `POST`.
2. Semaphore определяет по алиасу, какие интеграции он может запустить. Эндпоинт публичный — его защищают только алиас и способ аутентификации.
3. Каждая из этих интеграций проверяет запрос своим **способом аутентификации**. Запрос, не прошедший проверку, ничего не запускает.
4. Если вызов пришёл через **алиас проекта**, вычисляются **сопоставители** интеграции. Совпасть должны все, иначе интеграция пропускается.
5. Выполняется **извлечение значений**: части запроса превращаются в переменные и параметры задачи.
6. Задача создаётся и ставится в очередь — точно так же, как если бы шаблон запустили вручную.

Обработанный вызов получает ответ `204 No Content` с пустым телом независимо от того, было ли что-то запущено. О том, что именно запущено, сообщают заголовки ответа:

| Заголовок ответа | Значение |
|---|---|
| `X-Semaphore-Task-ID` | Созданная задача |
| `X-Semaphore-Template-ID` | Шаблон, который она выполняет |
| `X-Semaphore-Project-ID` | Проект, которому принадлежит задача |
| `X-Semaphore-Integration-ID` | Интеграция, запустившая задачу |
| `X-Semaphore-Inventory-ID` | Инвентарь задачи, если он есть |

Каждый вызов известного алиаса также попадает в [историю вызовов](#call-history) — именно туда стоит смотреть, когда вебхук работает не так, как ожидалось.

## Алиасы {#aliases}

Алиас — это случайная, неугадываемая часть URL вебхука: `/api/integrations/<random_string>`. Поддерживаются `GET` и `POST`. Алиасы бывают двух видов, и интеграция в каждый момент использует только один из них.

**Алиас проекта** создаётся кнопкой **Add Alias** над списком интеграций и является общим для всех интеграций проекта, у которых включён переключатель **Use project alias**. Один входящий запрос предлагается всем им, и каждая по своим сопоставителям решает, запускаться ли. Именно такой алиас стоит один раз передать GitHub или GitLab, а затем разводить события сопоставителями.

**Алиас интеграции** создаётся кнопкой **Add Alias** на странице самой интеграции и принадлежит только ей. Обращение к нему запускает интеграцию сразу — **сопоставители не вычисляются вовсе**. Используйте его, когда отправитель предназначен для одной задачи или когда тело запроса в формате, который сопоставители разобрать не могут.

:::warning
Переключатель **Use project alias** на странице интеграции определяет, какой вид алиаса работает. Пока он включён, интеграция отвечает на алиас проекта, а её собственные алиасы игнорируются; пока он выключен, алиас проекта до интеграции не доходит, и её сопоставители никогда не используются.
:::

В проекте может быть несколько алиасов обоих видов. Удаление алиаса значком корзины рядом с ним прекращает его работу сразу, но уже полученные через него вызовы остаются в истории.

## Аутентификация {#authentication}

Эндпоинт вебхука не защищён входом в систему, поэтому способ аутентификации — это то, что не даёт посторонним запускать ваши задачи. Выберите его в форме интеграции; **Auth secret** — это ключ из [хранилища ключей](/user-guide/key-store).

| Способ аутентификации | Что проверяет Semaphore | Auth secret |
|---|---|---|
| **None** | Ничего — любой, кто узнает URL, сможет запустить шаблон | — |
| **GitHub Webhooks** | `X-Hub-Signature-256` равен `sha256=` плюс HMAC-SHA256 тела запроса | Строка или пароль ключа «логин/пароль» |
| **Bitbucket Webhooks** | `X-Hub-Signature` таким же образом | Строка или пароль ключа «логин/пароль» |
| **Token** | Заголовок, указанный в **Auth header**, равен секрету | Строка или пароль ключа «логин/пароль» |
| **HMAC** | Заголовок, указанный в **Auth header**, содержит HMAC-SHA256 тела | Строка или пароль ключа «логин/пароль» |
| **HMAC (SHA-512)** | То же самое с HMAC-SHA512 | Строка или пароль ключа «логин/пароль» |
| **BasicAuth** | Заголовок `Authorization` содержит логин *и* пароль | Только ключ «логин/пароль» |

Ключ типа **Строка** использует как общий секрет своё значение; ключ «логин/пароль» — свой пароль, и только BasicAuth сравнивает ещё и логин. Ключ типа, который способ аутентификации использовать не может, приводит к отказу в запросе, а не к молчаливому игнорированию несоответствия.

### Аутентификация HMAC {#hmac-authentication}

Методы аутентификации HMAC (`hmac` / SHA-256 и `hmac-sha512` / SHA-512) проверяют, что тело вебхука подписано общим секретом.

Настройте:

1. **Auth header** — заголовок запроса, в котором передаётся подпись (например, `X-Signature` или `X-Hub-Signature-256`).
2. **Auth secret** — ключ типа **Строка** из хранилища ключей (секретом является его значение) или учётные данные «логин/пароль» (секретом является **пароль**).

Отправитель должен поместить в этот заголовок HMAC-дайджест необработанного тела запроса в виде **шестнадцатеричной строки без префикса** `sha256=` или `sha512=` (методы GitHub и Bitbucket этот префикс как раз ожидают, методы HMAC — нет). Semaphore сравнивает его с `HMAC-SHA256` или `HMAC-SHA512` тела, вычисленным с настроенным секретом.

Пример для SHA-512 с OpenSSL:

```bash
SECRET='your-webhook-secret'
BODY='{"event":"deploy"}'
SIG="$(printf '%s' "$BODY" | openssl dgst -sha512 -hmac "$SECRET" | awk '{print $2}')"

curl -X POST "https://semaphore.example.com/api/integrations/<alias>" \
  -H "Content-Type: application/json" \
  -H "X-Signature: ${SIG}" \
  --data "$BODY"
```

## Сопоставители {#matchers}

Сопоставитель — это одно условие на входящий запрос: *этот заголовок равен такому-то*, *это поле JSON содержит такую-то строку*. Благодаря сопоставителям один алиас проекта обслуживает много интеграций: GitHub отправляет все события на один и тот же URL, а сопоставители решают, какая интеграция реагирует на какое событие.

Сопоставитель только решает, запускать ли интеграцию. Он никогда не меняет задачу — для этого есть извлечение значений.

Сопоставители вычисляются **только для вызовов, пришедших через алиас проекта** (переключатель **Use project alias** включён). Обращение к собственному алиасу интеграции запускает её, не заглядывая в них.

### Поля сопоставителя {#matcher-fields}

| Поле | Значение |
|---|---|
| **Name** | Подпись для списка. Произвольный текст, в сравнении не участвует |
| **Match on** | **Body** или **Header** — откуда берётся значение |
| **Body Data Format** | **JSON** или **String**, показывается только для **Body** |
| **Key** | Имя заголовка или путь к полю в теле JSON |
| **Comparison Method** | `==`, `!=` или **Contains** |
| **Value** | Текст, с которым сравнивается значение из запроса |

**Match on: Header** — **Key** здесь имя заголовка, и регистр в нём не важен: `X-GitHub-Event` и `x-github-event` — один и тот же заголовок. Заголовок, которого в запросе нет, ведёт себя как отсутствующее значение (см. ниже). Если заголовок встречается несколько раз, сравнивается только первое значение.

**Match on: Body, JSON** — **Key** здесь путь внутри разобранного тела, он описан в следующем разделе. Тело, не являющееся корректным JSON, даёт отсутствующее значение для любого ключа.

**Match on: Body, String** — значением становится всё необработанное тело, а **Key** игнорируется. Форма всё равно требует ключ, потому что поле обязательное; поставьте дефис. Это единственный способ сопоставления с телом, которое не является JSON — используйте его вместе с **Contains**.

Поля **Key** и **Value** обязательны, поэтому сопоставителем нельзя проверить пустое значение. Чтобы реагировать на отсутствие поля, сравните его через `!=` со значением, которого у него никогда не бывает.

### Ключи JSON {#json-keys}

Ключ — это путь по документу JSON. Уровни разделяются точками, а элемент массива указывается индексом в квадратных скобках, начиная с нуля. Регистр в именах важен.

```json
{
  "ref": "refs/heads/main",
  "repository": { "name": "semaphore", "private": false },
  "commits": [
    { "id": "9fceb02", "message": "Fix the deploy" },
    { "id": "1c4a7b8", "message": "Bump the version" }
  ]
}
```

| Ключ | На что указывает |
|---|---|
| `ref` | `refs/heads/main` |
| `repository.name` | `semaphore` |
| `repository.private` | `false` |
| `commits.[0].id` | `9fceb02` |
| `commits.[1].message` | `Bump the version` |
| `commits` | Весь массив |
| `repository.url` | Ни на что — такого поля нет |

Тот же синтаксис используется в поле **Key** при извлечении значений.

### Как сопоставитель сравнивает значения {#how-a-matcher-compares-values}

Значение из запроса приводится к тексту и сравнивается с **Value** как текст, поэтому в поле **Value** не нужны ни кавычки, ни скобки, ни экранирование.

- **Строки** сравниваются буквально, и регистр важен: `Push` не совпадает с `push`.
- **Числа** сравниваются без дробной части, если её нет: `42` в теле совпадает со значением `42`, но не с `42.0`. Дробное число сравнивается как записано, поэтому `1.5` совпадает с `1.5`.
- **Логические значения** совпадают с `true` и `false`.
- **Отсутствующее значение** — нет заголовка, путь JSON не существует, в поле `null` или тело не является корректным JSON — сравнивается как буквальный текст `<nil>`. Из этого следует важное: `==` никогда не совпадёт с отсутствующим полем, а `!=` совпадёт с ним всегда.
- **Объекты и массивы** не имеют осмысленного текстового вида; не сравнивайте их. Направьте ключ на скалярное поле внутри.
- **Contains** — простая проверка подстроки с учётом регистра, без шаблонов и регулярных выражений.

### Несколько сопоставителей {#several-matchers}

У интеграции может быть любое число сопоставителей, и они объединяются по **И**: интеграция запускается только когда совпали все. Выразить *или* внутри одной интеграции нельзя — создайте для альтернативного условия вторую интеграцию на том же шаблоне.

:::warning
Интеграция, которая использует алиас проекта и **не имеет сопоставителей**, не запускается никогда: совпадать просто нечему. Добавьте хотя бы один сопоставитель или выключите **Use project alias** и обращайтесь к собственному алиасу интеграции.
:::

### Примеры сопоставителей {#matcher-examples}

| Цель | Match on | Формат | Key | Метод | Value |
|---|---|---|---|---|---|
| Только push в GitHub | Header | — | `X-GitHub-Event` | `==` | `push` |
| Только push в `main` | Body | JSON | `ref` | `==` | `refs/heads/main` |
| Любая ветка, кроме `main` | Body | JSON | `ref` | `!=` | `refs/heads/main` |
| Только теги | Body | JSON | `ref` | Contains | `refs/tags/` |
| Только влитые merge request в GitLab | Body | JSON | `object_attributes.state` | `==` | `merged` |
| Игнорировать коммиты бота | Body | JSON | `pusher.name` | `!=` | `dependabot` |
| Только опубликованные релизы GitHub | Body | JSON | `action` | `==` | `published` |
| Текстовое оповещение со словом про диск | Body | String | `-` | Contains | `disk` |

Первые две строки вместе — обычная конфигурация интеграции для развёртывания: тип события из заголовка и ветка из тела, причём совпасть должны оба условия.

## Извлечение значений {#value-extractors}

Извлекатель копирует одну часть входящего запроса в задачу, которая вот-вот запустится. Так вебхук передаёт в запускаемую автоматизацию ветку, хеш коммита, автора или версию релиза.

Извлечение выполняется всегда, через какой бы вид алиаса ни пришёл вызов, и происходит после успешной аутентификации и проверки сопоставителей.

### Поля извлекателя {#extractor-fields}

| Поле | Значение |
|---|---|
| **Name** | Подпись для списка. Произвольный текст |
| **Source of the Value** | **Body** или **Header** |
| **Data Type of Body** | **JSON** или **String**, показывается только для **Body** |
| **Key** | Имя заголовка или [ключ JSON](#json-keys) — синтаксис тот же, что у сопоставителей |
| **Variable Usage** | **Variables** или **Task Params** — куда передаётся значение |
| **Variable** | Имя, под которым значение попадёт в задачу |

При **Body** и **String** значением становится всё необработанное тело, а **Key** игнорируется — так же, как в сопоставителе.

### Что получает переменная {#what-the-variable-receives}

В отличие от сопоставителя, извлекатель ничего не приводит к тексту: значение JSON сохраняет свой тип, поэтому число остаётся числом, а объект — объектом.

| Что в запросе | Что получает переменная |
|---|---|
| Заголовок | Его текст; пустую строку, если заголовка нет |
| Строка, число или логическое значение JSON | То же значение вместе с типом |
| Объект или массив JSON | Весь объект или массив с сохранением структуры |
| `null` в JSON, несуществующий путь или тело, не являющееся корректным JSON | Ничего — переменная **вообще не задаётся**, и значение, определённое в шаблоне, остаётся на месте |
| Тело как **String** | Всё необработанное тело как текст |

Разница между «пусто» и «не задано» существенна: отсутствующий заголовок даёт задаче пустую строку, а отсутствующее поле JSON оставляет нетронутым собственное значение шаблона.

### Назначение переменной: Variables {#variable-usage-variables}

Значение попадает в переменные задачи — тот же набор, который заполняет поле **Variables** в диалоге запуска задачи. Semaphore передаёт их инструменту как дополнительные переменные (`--extra-vars` для Ansible, `-var` для Terraform), и они переопределяют одноимённый ключ из [группы переменных](/user-guide/environment) шаблона.

Назовите переменную точно так же, как [переменную опроса](/user-guide/task-templates/survey-vars) шаблона, и вебхук заполнит эту переменную опроса вместо человека.

### Назначение переменной: Task Params {#variable-usage-task-params}

Параметры задачи — это встроенные [подсказки](/user-guide/task-templates/prompts) шаблона, а не переменные для плейбука. Извлечённое значение передаётся без изменений, поэтому его тип в JSON должен совпадать с ожидаемым: `true`, а не `"true"`.

| Переменная | Для чего | Ожидает |
|---|---|---|
| `git_branch` | Для любого приложения | Ветку для checkout. Ведущий `refs/heads/` отбрасывается, поэтому `ref` из GitHub можно использовать как есть |
| `limit`, `tags`, `skip_tags` | Ansible | Список строк |
| `debug`, `dry_run`, `diff` | Ansible | `true` или `false` |
| `plan`, `destroy`, `auto_approve`, `upgrade`, `reconfigure` | Terraform, OpenTofu, Terragrunt | `true` или `false` |

Чтобы значение подействовало, шаблон должен разрешать переопределение: **Allow override branch in task** для `git_branch` и соответствующую подсказку для `limit`, `tags` и `skip_tags`. Без такого разрешения значение отбрасывается, и задача выполняется с настройкой самого шаблона.

### Пример извлечения: push в GitHub {#extractor-example-github-push}

Вебхук GitHub о push отправляет тело, которое начинается так:

```json
{
  "ref": "refs/heads/main",
  "after": "9fceb02d0ae598e95dc970b74767f19372d61af8",
  "repository": { "name": "semaphore", "default_branch": "main" },
  "pusher": { "name": "octocat", "email": "octocat@example.com" }
}
```

Четыре извлекателя превращают его в полностью описанную задачу:

| Name | Source | Формат | Key | Usage | Variable |
|---|---|---|---|---|---|
| Branch | Body | JSON | `ref` | Task Params | `git_branch` |
| Commit | Body | JSON | `after` | Variables | `COMMIT` |
| Author | Body | JSON | `pusher.name` | Variables | `AUTHOR` |
| Event | Header | — | `X-GitHub-Event` | Variables | `EVENT` |

Задача затем делает checkout `main` (префикс `refs/heads/` убирается за вас) и выполняется с переменными `COMMIT`, `AUTHOR` и `EVENT`, доступными плейбуку. Чтобы увидеть, что на самом деле пришло с реальным вызовом, откройте его на вкладке History и сверьте тело со своими ключами.

## Предустановленные параметры задачи {#task-parameters}

Как только в форме интеграции выбран шаблон, под ним появляются его собственные параметры запуска: сообщение, переменные опроса, инвентарь, ветка Git (если шаблон разрешает её переопределять) и подсказки приложения. Всё заданное здесь становится значением по умолчанию для каждой задачи, которую запускает эта интеграция, поэтому то, что никогда не меняется — инвентарь, фиксированное сообщение, — указывайте здесь, а не в извлекателе.

Извлечение применяется поверх этих значений: переменная или параметр задачи, полученные извлекателем, заменяют одноимённое предустановленное значение, а если извлекатель ничего не нашёл, предустановка сохраняется.

## Интеграции с воркфлоу <FeatureState feature="workflows" /> {#workflow-integrations}

Интеграция может запускать [воркфлоу](/user-guide/workflows) вместо одного шаблона. Переключите **Runs** на **Workflow** в форме интеграции и выберите воркфлоу.

Извлечение значений работает так же, с одним отличием: **Variable Usage** игнорируется, и каждое извлечённое значение передаётся как ответ на опрос воркфлоу под именем из **Variable**. Воркфлоу проверяет эти ответы и доставляет их своим узлам через их привязки, поэтому значение, к которому не привязан ни один узел, до задачи не доходит. Успешный вызов сообщает `X-Semaphore-Workflow-ID` и `X-Semaphore-Workflow-Run-ID` в дополнение к заголовкам задачи.

## История вызовов {#call-history}

На вкладке **History** страницы интеграций перечислены все вызовы, которые проект получил через любой из своих алиасов, начиная с самых свежих. История переживает и алиас, и интеграцию, и запущенную задачу, потому что хранится для проекта в целом, а не для отдельной интеграции.

| Столбец | Что показывает |
|---|---|
| **Time** | Когда поступил вызов |
| **Integration** | Обработавшую его интеграцию, под ней — алиас; щелчок по алиасу фильтрует список по нему |
| **Source IP** | Адрес, с которого пришёл вызов |
| **Method** | `GET` или `POST` |
| **Status** | Что интеграция сделала с вызовом и почему |
| **Task** | Запущенную задачу или запуск воркфлоу |
| **Duration** | Сколько интеграция обрабатывала вызов |

Возможны четыре статуса:

| Статус | Значение |
|---|---|
| `ok` | Задача или запуск воркфлоу начались |
| `unauthorized` | Запрос не прошёл аутентификацию интеграции |
| `skipped` | Сопоставители не совпали или алиас не запустил ни одной интеграции |
| `error` | Запуск был предпринят и не удался — шаблон удалён, опрос не принял значения |

Щелчок по строке открывает вызов вместе с телом запроса в полученном виде (первые 64 КиБ; если тело было длиннее, показываются и сохранённый, и исходный размер). Заголовки запроса **не сохраняются никогда**: в них передаются подпись или токен, которыми аутентифицировался отправитель. Тело вызова, не прошедшего аутентификацию, тоже не сохраняется — такой запрос может отправить любой, кто знает URL.

Фильтруйте список по интеграции и по алиасу элементами управления над таблицей, а перемещайтесь по страницам стрелками под ней. Срока хранения у истории нет — она растёт до удаления проекта.

## Устранение неполадок {#troubleshooting}

| Симптом | Что проверить |
|---|---|
| В History вообще нет записи | Алиас в URL неверен или удалён. Обращение к собственному алиасу интеграции при включённом **Use project alias** тоже нигде не записывается |
| `unauthorized` | Имя заголовка аутентификации, ключ в хранилище ключей и то, отправляет ли отправитель подпись с префиксом `sha256=`, которого ждёт метод. GitHub и Bitbucket используют свои собственные заголовки независимо от **Auth header** |
| `skipped`, причина *No integration matched the alias* | Алиас существует, но ни у одной интеграции проекта не включён **Use project alias** |
| `skipped`, причина *No matcher matched the request* | Откройте вызов и сверьте его тело со своими сопоставителями. Помните, что отсутствующее поле никогда не совпадает по `==`, что регистр в ключах важен и что у **Contains** нет шаблонов. Интеграция вообще без сопоставителей пропускается по той же причине |
| Задача запускается, но переменная пуста или отсутствует | Ключ JSON не соответствует содержимому (откройте вызов и посмотрите тело), значение было `null` или имя в **Variable** не совпадает с переменной опроса, которую нужно заполнить |
| Ветка не переопределяется | Шаблону нужен флаг **Allow override branch in task**, а извлекатель должен записывать параметр задачи `git_branch` |
| С одного вызова запускается несколько задач | Алиас проекта используют несколько интеграций, и у всех совпали сопоставители. Сделайте сопоставители строже или выдайте интеграциям собственные алиасы |
