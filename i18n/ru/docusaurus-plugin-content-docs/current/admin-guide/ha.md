# Высокая доступность <Enterprise />

:::info
Высокая доступность доступна в редакции **Semaphore Enterprise**.
:::

Semaphore UI поддерживает развёртывание в режиме высокой доступности (HA) active-active, при котором несколько экземпляров работают одновременно за балансировщиком нагрузки. Каждый экземпляр полностью способен обрабатывать запросы UI, вызовы API, запланированные задания и выполнение задач. Если один экземпляр выходит из строя, остальные узлы продолжают работать без перерыва.

## Архитектура {#architecture}

Типичное развёртывание active-active состоит из следующих компонентов:

**Балансировщик нагрузки** — пользователи подключаются через балансировщик нагрузки (например, NGINX, HAProxy или облачный балансировщик). Балансировщик распределяет HTTP- и WebSocket-трафик между доступными узлами Semaphore.

**Узлы Semaphore** — на каждом узле работает идентичный экземпляр Semaphore UI. Любой узел может принимать запросы пользователей, запускать задания автоматизации, обрабатывать запланированные задачи и отправлять обновления в реальном времени. Все узлы равноправны — нет основного или резервного узла.

**Общая база данных** — все экземпляры подключаются к общей базе данных PostgreSQL или MySQL. База данных выступает единым источником истины для проектов, шаблонов, инвентарей, расписаний, истории задач, учётных записей пользователей и конфигурации RBAC.

:::warning
SQLite и BoltDB не поддерживаются для HA-развёртываний. Используйте PostgreSQL или MySQL.
:::

**Redis** — Redis обеспечивает слой координации, который позволяет нескольким узлам работать как единая система. Он выполняет три функции:

* **Распределённые блокировки** гарантируют, что конкретное задание в каждый момент времени выполняет только один экземпляр, предотвращая дублирование выполнения задач.
* **Общее состояние очереди задач** поддерживает очередь задач так, что каждое задание берёт ровно один worker. Все узлы видят одну и ту же очередь и координируют выполнение.
* **Обмен сообщениями Pub/Sub** позволяет узлам рассылать события, такие как обновления задач, уведомления кластера, инвалидация кэша и изменения состояния UI. Это поддерживает синхронизацию всех узлов в реальном времени.

## Предварительные требования {#prerequisites}

Перед настройкой HA вам понадобятся:

* Ключ подписки **Semaphore Enterprise**.
* Общая база данных **PostgreSQL** или **MySQL**, доступная со всех узлов.
* Сервер **Redis** или развёртывание **Redis Sentinel**, доступное со всех узлов. Redis Cluster не поддерживается.
* **Балансировщик нагрузки**, поддерживающий HTTP- и WebSocket-трафик.
* Два или более сервера для запуска экземпляров Semaphore.

Все узлы Semaphore должны использовать одну и ту же базу данных, один и тот же бэкенд Redis и одинаковую конфигурацию (за исключением `ha.node_id`, который должен быть уникальным для каждого узла).

## Конфигурация {#configuration}

Включите HA, добавив блок `ha` в `config.json` на каждом узле:

```json
{
  "dialect": "postgres",
  "postgres": {
    "host": "db.example.com:5432",
    "name": "semaphore",
    "user": "semaphore",
    "pass": "***"
  },

  "ha": {
    "enabled": true,
    "node_id": "node-1",
    "redis": {
      "addr": "redis.example.com:6379",
      "db": 0,
      "pass": "***"
    }
  },

  "cookie_hash": "...",
  "cookie_encryption": "...",
  "access_key_encryption": "..."
}
```

У каждого узла должен быть уникальный `ha.node_id`. Вся остальная конфигурация должна быть идентичной на всех узлах.

### Переменные окружения {#environment-variables}

Также HA можно настроить с помощью переменных окружения:

```bash
SEMAPHORE_HA_ENABLED=true
SEMAPHORE_HA_NODE_ID=node-1
SEMAPHORE_HA_REDIS_ADDR=redis.example.com:6379
SEMAPHORE_HA_REDIS_DB=0
SEMAPHORE_HA_REDIS_PASS=***
```

### Redis Sentinel {#redis-sentinel}

Чтобы кластер переживал отказ самого сервера Redis, укажите вместо одного адреса развёртывание [Redis Sentinel](https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/). Задайте для `ha.engine` значение `redis_sentinel` и опишите настройки Sentinel в `ha.redis_sentinel`:

```json
{
  "ha": {
    "enabled": true,
    "node_id": "node-1",
    "engine": "redis_sentinel",
    "redis_sentinel": {
      "master_name": "mymaster",
      "addrs": ["sentinel-1.example.com:26379", "sentinel-2.example.com:26379", "sentinel-3.example.com:26379"],
      "pass": "***"
    }
  }
}
```

Каждый узел запрашивает у sentinel'ов текущий master и отслеживает failover без перезапуска: задача, выполнявшаяся в момент смены master'а, продолжает работу, а новые задачи, расписания и обновления в реальном времени продолжаются на повышенной реплике.

Та же настройка с помощью переменных окружения (список sentinel'ов — JSON-массив):

```bash
SEMAPHORE_HA_ENABLED=true
SEMAPHORE_HA_NODE_ID=node-1
SEMAPHORE_HA_ENGINE=redis_sentinel
SEMAPHORE_HA_REDIS_SENTINEL_MASTER_NAME=mymaster
SEMAPHORE_HA_REDIS_SENTINEL_ADDRS='["sentinel-1.example.com:26379","sentinel-2.example.com:26379","sentinel-3.example.com:26379"]'
SEMAPHORE_HA_REDIS_SENTINEL_PASS=***
```

Примечания:

* `ha.engine` определяет, какой блок считывается. `redis` (значение по умолчанию) считывает `ha.redis`; `redis_sentinel` считывает `ha.redis_sentinel`. Другой блок, если он присутствует, игнорируется, а при запуске в лог выводится предупреждение.
* При `redis_sentinel` обязательны `master_name` и хотя бы один адрес в `addrs`; без них узел откажется запускаться.
* `user` и `pass` используются для аутентификации на узлах данных Redis. Если сами sentinel'ы требуют аутентификации (`requirepass` в `sentinel.conf`), задайте также `sentinel_user` и `sentinel_pass`.
* `tls` и `tls_skip_verify` применяются как к подключениям к Sentinel, так и к подключениям к узлам данных Redis.

## Балансировщик нагрузки {#load-balancer}

Разместите балансировщик нагрузки перед узлами Semaphore для распределения трафика. Балансировщик должен поддерживать **WebSocket-соединения** для обновления UI в реальном времени.

### Пример для NGINX {#nginx-example}

```nginx
upstream semaphore {
    server node1.example.com:3000 max_fails=3 fail_timeout=10s;
    server node2.example.com:3000 max_fails=3 fail_timeout=10s;
    server node3.example.com:3000 max_fails=3 fail_timeout=10s;
}

server {
    listen 443 ssl;
    server_name semaphore.example.com;

    ssl_certificate     /etc/ssl/certs/semaphore.crt;
    ssl_certificate_key /etc/ssl/private/semaphore.key;

    location / {
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        
        proxy_pass http://semaphore;

        proxy_connect_timeout 3s;
        proxy_send_timeout 60s;
        proxy_read_timeout 60s;

        proxy_next_upstream error timeout invalid_header http_500 http_502 http_503 http_504;
        proxy_next_upstream_tries 3;
    }


    location /api/ws {
        
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        proxy_pass http://semaphore;
        
        proxy_connect_timeout 3s;
        proxy_send_timeout 1h;
        proxy_read_timeout 1h;

        proxy_next_upstream error timeout http_502 http_503 http_504;
        proxy_next_upstream_tries 3;
    }
}
```

Подробнее о настройке NGINX см. в разделе [Обратный прокси](/admin-guide/reverse-proxy/nginx).

## Как происходит выполнение заданий {#how-job-execution-works}

В многоузловом развёртывании выполнение задач проходит по координированной схеме:

1. **Пользователь запускает задачу.** Пользователь запускает задание через UI или API. Запрос может попасть на любой узел Semaphore.
2. **Метаданные задачи сохраняются.** Принявший запрос узел записывает метаданные задачи в базу данных и сигнализирует о новой работе через Redis.
3. **Узел берёт задачу.** Один из доступных узлов получает задачу из Redis, захватывает распределённую блокировку и помечает задачу как выполняющуюся в базе данных.
4. **Задача выполняется.** Узел выполняет задачу локально или делегирует её [удалённому runner'у](/admin-guide/runners). Прогресс и логи записываются обратно в базу данных.
5. **Результаты рассылаются.** Обновления задачи распространяются через Redis Pub/Sub, поэтому все узлы и подключённые клиенты UI остаются синхронизированными.

## Как HA устроен изнутри {#under-the-hood}

Узлы Semaphore никогда не общаются друг с другом напрямую. Всё, о чём им нужно договориться, проходит через Redis: кто жив, какая задача какому узлу принадлежит, кто запускает расписание и какие сообщения UI нужно переслать. Каждая часть этого состояния — небольшой набор ключей Redis со сроком жизни, поэтому упавший узел не может надолго оставить после себя мусор. Долговременные данные (задачи, шаблоны, логи, runner'ы) всегда живут в базе данных; в Redis хранится только координационное состояние.

Все ключи используют фиксированные префиксы `ha:` и `tasks:`. Они не настраиваются, поэтому два кластера Semaphore на одном сервере Redis должны использовать разные номера баз (`ha.redis.db`).

### Реестр узлов {#node-registry}

Каждый узел регистрируется при старте и затем обновляет свою запись каждые 10 секунд. Запись истекает через 30 секунд, поэтому узел, переставший её обновлять, считается мёртвым самое большее через полминуты. При штатной остановке узел удаляет свою запись сразу.

| Ключ | Тип | Назначение |
| --- | --- | --- |
| `ha:node:<node_id>` | строка, JSON | Heartbeat одного узла: `node_id`, `started_at`, `version`, `last_beat`. Истекает через 30 с после последнего обновления. |
| `ha:nodes` | множество | Идентификаторы всех зарегистрированных узлов. Участников, чей heartbeat-ключ истёк, вычищают остальные узлы. |

Именно реестр узлов показывает панель кластера, и к нему же обращается сборщик осиротевших задач (см. ниже), чтобы решить, жив ли ещё владелец задачи.

### Очередь задач и выполняющиеся задачи {#task-queue}

Очередь задач общая, поэтому задачу, запущенную на одном узле, может взять в работу, отслеживать и завершать любой другой. В Redis хранятся только идентификаторы задач и несколько временных полей; саму задачу из базы данных загружает тот узел, которому она понадобилась.

| Ключ | Тип | Назначение |
| --- | --- | --- |
| `tasks:queue` | список | Идентификаторы задач, ожидающих отправки на выполнение, по порядку. |
| `tasks:claim:<task_id>` | строка | Идентификатор узла, которому принадлежит задача. Записывается атомарно вместе с удалением из очереди, поэтому задачу забирает ровно один узел. Истекает через 5 минут; владелец продлевает его каждую минуту. |
| `tasks:running` | множество | Идентификаторы задач, которые выполняются в данный момент. |
| `tasks:active:<project_id>` | множество | Идентификаторы активных задач проекта (ожидающих или выполняющихся). Используется для ограничения параллельности в проекте. |
| `tasks:task_project` | хеш | `task_id` → `project_id`, чтобы любой узел мог загрузить задачу из базы данных. |
| `tasks:aliases` | хеш | `alias` → `task_id` для задач, к которым обращаются по псевдониму. |
| `tasks:runtime:<task_id>` | хеш | Поля, меняющиеся по ходу выполнения, например идентификатор runner'а и имя запустившего пользователя. |
| `tasks:finalize:<task_id>` | строка | Блокировка узла, записывающего итоговый результат задачи, выполнявшейся на удалённом runner'е. Истекает через 5 минут. |

Записи в `tasks:task_project`, `tasks:aliases` и `tasks:runtime:*` удаляются по завершении задачи и дополнительно истекают через 7 дней на всякий случай.

Узел забирает задачу из очереди одной атомарной операцией: проверяет, что задача всё ещё в очереди, записывает владельца, удаляет задачу из очереди и добавляет её во множество выполняющихся. Если два узла попытаются сделать это одновременно, получится только у одного.

**Сборщик осиротевших задач.** Раз в минуту каждый узел просматривает выполняющиеся задачи, владелец которых мёртв: запись владельца истекла или пропал его heartbeat. Задача, которую база данных уже считает завершённой, просто удаляется из Redis. Задача, которую так и не передали runner'у, возвращается в очередь, чтобы её отправил живой узел. Задача, которая уже выполняется на runner'е, не трогается: runner продолжает работу, а задача будет вычищена, когда база данных покажет её завершённой.

### Блокировки {#locks}

Блокировка — это одиночный ключ, создаваемый командой `SET NX`: блокировку держит тот узел, которому удалось создать ключ. У каждой блокировки есть срок жизни, а долго удерживаемые блокировки владелец продлевает, поэтому упавший узел освобождает свои блокировки автоматически.

| Ключ | Срок жизни | Назначение |
| --- | --- | --- |
| `ha:sched:lock:<schedule_id>:<minute>` | 55 с | Одна блокировка на расписание в минуту. Узел, создавший её, запускает расписание; остальные пропускают запуск. |
| `ha:wf:lock:<project_id>:<run_id>` | 30 с, продлевается каждые 10 с | Конкретный запуск workflow в каждый момент продвигает только один узел. |
| `ha:wf:start:<project_id>:<template_id>` | 10 с | Короткая блокировка на время создания нового запуска workflow, чтобы два узла не запустили один workflow дважды. |
| `ha:audit:export:<destination_id>` | 30 с, продлевается каждые 10 с | События аудита в конкретное назначение экспортирует только один узел. Если Redis недоступен, не экспортирует никто, поэтому события никогда не отправляются дважды. |

Блокировки расписаний и workflow при сбое открываются: если до Redis не достучаться, узел продолжает работу, а не пропускает её, и корректность результата обеспечивают условные обновления в базе данных. Аренда экспорта аудита при сбое закрывается, потому что повторный экспорт отменить нельзя.

### Каналы Pub/Sub {#pubsub-channels}

| Канал | Назначение |
| --- | --- |
| `ha:ws:broadcast` | WebSocket-сообщения для UI. Узел доставляет сообщение своим подключённым браузерам и публикует его сюда; остальные узлы пересылают его своим. |
| `tasks:events` | Изменения очереди задач и множества выполняющихся, обновления полей времени выполнения и запросы на принудительную остановку. По этим событиям узлы поддерживают актуальной свою картину очереди в памяти и останавливают задачу, остановить которую попросил другой узел. |

Сообщения содержат идентификатор узла-отправителя, поэтому узел игнорирует собственные сообщения.

### Ключи кэша runner'ов {#runner-cache-keys}

Ключи `ha:runner:*` принадлежат [кэшу runner'ов](#runner-cache), описанному в следующем разделе.

## Кэш runner'ов {#runner-cache}

Каждый запрос, который [runner](/admin-guide/runners) отправляет серверу, содержит его токен, и прежде чем что-либо делать, сервер должен превратить этот токен в запись runner'а. Runner'ы опрашивают сервер каждые несколько секунд, а во время выполнения задания отправляют прогресс каждую секунду, поэтому без кэша каждый такой запрос стоил бы обращения к базе данных. Кэш runner'ов отвечает на большинство из них из памяти.

Одиночный узел держит кэш в собственной памяти. В режиме HA этого недостаточно: если вы изменили runner на узле A, узел B не должен продолжать отдавать старую запись. Поэтому в режиме HA кэш живёт в Redis и общий для всех узлов, а изменение, сделанное через любой узел, видно всем сразу.

:::note
Этот кэш — не то же самое, что действие **Очистить кэш** на странице Runner'ов. То действие просит сам runner удалить рабочие каталоги на его машине.
:::

### Что кэшируется и как долго {#runner-cache-ttl}

Кэшируется запись runner'а без тегов и без токена. Токен никогда не попадает в Redis: ключ строится из SHA-256-хеша токена, а поле токена обнуляется перед сохранением записи.

Запись живёт не дольше 30 секунд. На практике она сбрасывается гораздо раньше, потому что любое изменение через Semaphore немедленно инвалидирует кэш:

* Создание, изменение, удаление или перерегистрация runner'а, а также удаление проекта сбрасывают **все** закэшированные записи на всех узлах.
* Heartbeat runner'а сбрасывает **только запись этого runner'а**, поэтому сохранённое время «последней активности» остаётся свежим, не задевая остальных. Heartbeat записывается не чаще, чем раз в треть `runners.offline_timeout_sec`, но не реже чем раз в 45 секунд; при таймауте по умолчанию в 120 секунд это каждые 40 секунд.

Срок в 30 секунд важен только для изменений в обход Semaphore, например при прямом редактировании таблицы `runner` или восстановлении из резервной копии.

### Как предотвращается запись устаревших данных {#runner-cache-generation}

Запрос, не нашедший запись в кэше, читает runner из базы данных и затем сохраняет его. Между этими двумя шагами другой узел может изменить runner. Чтобы запрос никогда не закэшировал то, что прочитал до изменения, кэш ведёт счётчик, растущий при каждой инвалидации. Запрос запоминает значение счётчика перед обращением к базе данных, и сохранение отклоняется, если счётчик за это время сдвинулся. Каждый шаг выполняется одним Lua-скриптом в Redis, поэтому счётчик и запись читаются и пишутся вместе.

### Ключи Redis {#runner-cache-redis-keys}

| Ключ | Тип | Назначение |
| --- | --- | --- |
| `ha:runner:gen` | строка, целое число | Счётчик. Растёт на единицу при каждой инвалидации — как всего кэша, так и одного runner'а. |
| `ha:runner:inv` | строка, целое число | Значение счётчика на момент последней полной инвалидации. Оно входит в ключ каждой записи, поэтому полная инвалидация делает все существующие записи недостижимыми разом; затем они истекают сами. |
| `ha:runner:token:<inv>:<sha256(token)>` | строка, бинарная | Закэшированная запись runner'а. Истекает через 30 с. |
| `ha:runner:forgot:<sha256(token)>` | строка, целое число | Значение счётчика на момент последнего heartbeat этого runner'а. Запрос, начавшийся до heartbeat, не сможет сохранить запись в состоянии до него. Истекает через 30 с. |

Панель кластера показывает число ключей `ha:runner:token:*` как размер кэша runner'ов.

### Поведение при проблемах с Redis {#runner-cache-failures}

Кэш никогда не приводит к ошибке запроса runner'а. Каждая операция с кэшем ограничена 500 миллисекундами; если Redis медленный или недоступен, запрос считается промахом и идёт в базу данных, а в кэш ничего не записывается. Единственный случай, о котором стоит знать, — инвалидация, не удавшаяся потому, что Redis лежал в момент изменения runner'а: тогда другие узлы могут отдавать старую запись, пока она не истечёт, то есть не дольше 30 секунд. Такой сбой пишется в лог с уровнем error.

## Масштабирование с помощью runner'ов {#scaling-with-runners}

HA также позволяет горизонтально масштабировать выполнение задач. Вместо запуска заданий только на самих узлах Semaphore выполнение можно делегировать нескольким [runner'ам](/admin-guide/runners). Это позволяет:

* Распределять нагрузку по вашей инфраструктуре.
* Масштабировать мощность автоматизации независимо от слоя web/API.
* Изолировать среды выполнения, чтобы ограничить масштаб последствий сбоев.
* Выполнять задачи параллельно на множестве узлов.

Инструкции по настройке см. в разделе [Runner'ы](/admin-guide/runners).

## Преимущества {#benefits}

* **Повышенная надёжность** — если один экземпляр выходит из строя, остальные продолжают обслуживать трафик и выполнять задания.
* **Обслуживание без простоя** — узлы можно обновлять или перезапускать по отдельности, не останавливая систему.
* **Горизонтальная масштабируемость** — добавляйте узлы Semaphore за балансировщиком нагрузки для увеличения мощности.
* **Отсутствие зависимости от основного узла** — все узлы равноправны, что избавляет от сложных механизмов failover.
* **Согласованное состояние кластера** — общая база данных и координация через Redis поддерживают синхронизацию всех экземпляров.

## FAQ {#faq}

### Что такое высокая доступность active-active? {#what-is-active-active-high-availability}

HA в режиме active-active означает, что несколько экземпляров приложения работают одновременно и все они обслуживают запросы. Основного узла нет — любой экземпляр может обрабатывать трафик и выполнять задания.

### Почему Semaphore использует Redis в режиме HA? {#why-does-semaphore-use-redis-in-ha-mode}

Redis выступает слоем координации между экземплярами. Он предоставляет распределённые блокировки, общее состояние очереди задач и обмен сообщениями Pub/Sub, чтобы узлы не выполняли одно и то же задание одновременно.

### Какую базу данных использовать для HA-развёртываний? {#what-database-should-i-use-for-ha-deployments}

Semaphore поддерживает PostgreSQL и MySQL в качестве общей базы данных. SQLite и BoltDB нельзя использовать в режиме HA, так как они не поддерживают одновременный доступ из нескольких процессов.

### Что произойдёт, если Redis выйдет из строя? {#what-happens-if-redis-fails}

При одном сервере Redis (`ha.engine: redis`) узлы не смогут координироваться, пока Redis не вернётся в работу. При использовании [Redis Sentinel](#redis-sentinel) sentinel'ы повышают реплику, и каждый узел Semaphore автоматически переключается на неё — обычно в течение нескольких секунд и без перезапуска.

### Что произойдёт, если один узел Semaphore выйдет из строя? {#what-happens-if-one-semaphore-node-fails}

Балансировщик нагрузки направит трафик на оставшиеся узлы. Выполняющиеся задания продолжат работу на других экземплярах, а новые задания будут подхвачены любым доступным узлом.

### Можно ли масштабироваться горизонтально? {#can-i-scale-horizontally}

Да. Вы можете добавлять узлы Semaphore за балансировщиком нагрузки для увеличения мощности web/API и добавлять [runner'ы](/admin-guide/runners) для увеличения мощности выполнения задач.
