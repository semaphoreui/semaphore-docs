# Журнал аудита

Журнал аудита — это след действий для безопасности: кто что сделал, откуда, с каким объектом и с каким
результатом. Его читают аналитики безопасности и специалисты по соответствию требованиям, обычно в SIEM.
У каждого события стабильная документированная схема, поэтому аналитик может писать правила обнаружения,
не зная внутреннего устройства Semaphore.

Журнал аудита отделён от [журнала активности](/admin-guide/logs). Журнал активности — это лента для
пользователей проекта. Журнал аудита — это след для тех, кто проверяет, что система используется правильно.

## Как это работает {#overview}

Когда журнал аудита включён, Semaphore записывает событие для каждого действия, важного для безопасности,
которое приходит через веб-интерфейс или API: входы и выходы, проверки MFA, изменения пользователей,
участников проектов, ролей и прав, API-токены и системные настройки. Отклонённые запросы тоже записываются:
неудачный вход, неизвестный или просроченный API-токен, отказ в доступе, заблокированный межсайтовый запрос.

События хранятся в базе данных Semaphore. Semaphore Pro может отправлять их в SIEM, см.
[Экспорт в SIEM](#siem-export).

## Схема события {#event-schema}

Каждое событие — это JSON-объект с одним и тем же набором полей. Список событий, их исходы, причины и
метаданные см. в разделе [События аудита](/reference/audit-events).

| Поле | Описание |
| --- | --- |
| `event_id` | Уникальный ID события. По нему удаляют дубликаты в SIEM. |
| `seq` | Порядковый номер без пропусков, растёт с каждым событием. По нему упорядочивают события. |
| `timestamp` | Время события в UTC. |
| `schema_version` | Версия этой схемы. Меняется, только когда поле переименовано, удалено или сменило тип. |
| `category` | `auth`, `iam`, `resource`, `secret`, `task`, `runner`, `system` или `audit`. |
| `event_code` | К чему относится событие, например `iam.api_token`. |
| `type` | Вид изменения: `creation`, `change`, `deletion`, `access`, `start`, `end`, `denied` или `info`. |
| `action` | Что было сделано, например `create`. |
| `outcome` | `success` или `failure`. |
| `reason` | Почему действие не удалось, из фиксированного списка для каждого события. Пусто при успехе. |
| `actor` | Кто действовал: его `type` (`user`, `anonymous`, `system`, `runner`, `integration`), `id` и `name`. Для пользователя также `auth` (`session` или `api_token`), а для API-токена — `token_fingerprint`. |
| `source` | Для запросов к веб-интерфейсу и API: `ip` и `user_agent` клиента. |
| `target` | Объект действия: его `type`, `id` и `name`. |
| `scope` | `project_id` для событий внутри проекта. |
| `request_id` | ID HTTP-запроса. Semaphore также возвращает его в заголовке ответа `X-Request-ID`. |
| `instance_id` | Имя этой установки Semaphore из `audit.instance_id`. |
| `node_id` | Узел, записавший событие, когда включена [высокая доступность](/admin-guide/ha). |
| `metadata` | Дополнительные сведения, зависящие от события. |

`timestamp` — это время базы данных с точностью до микросекунд, на SQLite — до миллисекунд. Упорядочивайте
события по `seq`: у двух событий может совпасть время, но никогда не совпадёт `seq`.

В MySQL столбец `created` таблицы `audit_event` использует часовой пояс параметра подключения `loc`,
по умолчанию UTC. `timestamp` каждого события всегда в UTC.

Каждый запуск сервера записывает `audit.lifecycle` с действием `start`. События остановки нет: остановка,
сбой или выключение журнала аудита видны как разрыв во времени перед следующим `start`.

## Что никогда не записывается {#never-recorded}

Журнал аудита никогда не содержит паролей, одноразовых кодов, секретов и QR-кодов TOTP, кодов
восстановления, сессионных cookie, токенов, кодов и утверждений OAuth, закрытых ключей, парольных фраз,
значений секретов, значений окружения и опросов, тел вебхуков, вывода задач, адресов электронной почты и URL.
API-токен идентифицируется только по отпечатку: первым 16 шестнадцатеричным символам его хеша SHA-256.

ID пользователя и имя пользователя идентифицируют того, кто действовал. Неудачный вход записывает введённый
логин, обрезанный до 64 байт, потому что без него невозможно расследовать неудачные входы.

## Включите журнал аудита {#enable}

Задайте `audit.enabled` и дайте установке имя в `audit.instance_id`. Имя — это от 1 до 255 печатных символов
ASCII без пробелов, и оно попадает в каждое событие.

```json
{
  "audit": {
    "enabled": true,
    "instance_id": "prod-eu",
    "trusted_proxy_cidrs": ["10.0.0.0/8"]
  }
}
```

Или через переменные окружения:

```bash
SEMAPHORE_AUDIT_ENABLED=true
SEMAPHORE_AUDIT_INSTANCE_ID=prod-eu
SEMAPHORE_AUDIT_TRUSTED_PROXY_CIDRS='["10.0.0.0/8"]'
```

Перезапустите Semaphore, чтобы применить изменение. Все параметры см. в разделе
[Конфигурация](/reference/configuration).

## Адрес клиента за обратным прокси {#trusted-proxies}

За обратным прокси непосредственный собеседник Semaphore — это прокси, а адрес клиента берётся из
заголовка `X-Forwarded-For` или `X-Real-IP`. Semaphore читает эти заголовки, только если непосредственный
собеседник входит в `audit.trusted_proxy_cidrs`. Иначе записывается его собственный адрес, поэтому клиент не
может подделать свой адрес.

Указывайте в `audit.trusted_proxy_cidrs` только свои обратные прокси, никогда не сети клиентов. Клиент внутри
доверенного диапазона может подставить любой адрес в `X-Forwarded-For`.

Записывается самый правый адрес в `X-Forwarded-For`, который не является доверенным прокси.
`X-Real-IP` используется, только когда нет `X-Forwarded-For`, и только если у него одно значение.

## Хранение {#storage}

События хранятся в базе данных Semaphore и никогда не удаляются: в этой версии нет срока хранения.
Планируйте размер базы данных с учётом числа входов и изменений в вашей установке.

## Соответствие требованиям {#compliance}

Semaphore записывает события, нужные для этих требований. Сам по себе он не делает вашу установку
соответствующей им.

| Требование | Чем покрыто | Статус |
| --- | --- | --- |
| PCI DSS 10.2.1.1 доступ к конфиденциальным данным (аналог: секреты) | `iam.mfa/view_qr` | Доступно |
| PCI DSS 10.2.1.1 доступ к конфиденциальным данным (аналог: секреты) | `resource.project_backup/export` | Запланировано |
| PCI DSS 10.2.1.2 действия администраторов / ISO 27002 8.15 использование привилегий | `iam.*`, `system.*` | Доступно |
| PCI DSS 10.2.1.2 действия администраторов / ISO 27002 8.15 использование привилегий | `resource.*`, `secret.*` | Запланировано |
| PCI DSS 10.2.1.2 действия администраторов / ISO 27002 8.15 использование привилегий | `runner.*`, `task.control`, `task.history` | Запланировано |
| PCI DSS 10.2.1.3 доступ к журналам аудита | Неприменимо: Semaphore не даёт доступа к журналу аудита. | — |
| PCI DSS 10.2.1.4 неудачные попытки логического доступа / ISO отклонённые попытки доступа | `auth.login` failure, `auth.mfa` failure, `auth.api_token/reject`, `auth.authorization/deny`, `auth.csrf/block` | Доступно |
| PCI DSS 10.2.1.4 неудачные попытки логического доступа / ISO отклонённые попытки доступа | `runner.lifecycle/register` failure | Запланировано |
| PCI DSS 10.2.1.5 изменения учётных данных для идентификации и аутентификации | `iam.user*`, `iam.mfa`, `iam.api_token`, `iam.external_identity`, `iam.membership`, `iam.*role*` | Доступно |
| PCI DSS 10.2.1.5 изменения учётных данных для идентификации и аутентификации | `runner.credential` | Запланировано |
| PCI DSS 10.2.1.6 запуск, остановка и приостановка журналов аудита / ISO активация систем безопасности | `audit.lifecycle/start`; остановка видна как разрыв перед ним | Доступно |
| PCI DSS 10.2.1.7 создание и удаление системных объектов | `resource.*` create/delete | Запланировано |
| PCI DSS 10.2.1.7 создание и удаление системных объектов | `runner.lifecycle` create/delete | Запланировано |
| PCI DSS 10.2.2 обязательные поля | `actor`, `event_code` и `action`, `timestamp`, `outcome`, `source` или `node_id`, `target` или `scope` | Доступно |
| PCI DSS 10.3.3 оперативное резервное копирование на центральный сервер журналов | Экспорт в SIEM по Syslog+TLS | Доступно |
| PCI DSS 10.3.3 оперативное резервное копирование на центральный сервер журналов | Экспорт в SIEM по Splunk HEC | Запланировано |

Запланированные события в этой версии не записываются.

## Что не записывается в этой версии {#not-recorded}

- Действия, выполненные командой `semaphore` на сервере, например `user add` или `user token`. Они меняют
  базу данных напрямую, а тот, кто может их выполнить, может изменить и таблицу аудита.
- Удаление лицензии, настройки приложений, очистка состояния задач HA, псевдонимы инвентарей Terraform,
  запуски workflow и приглашения в проект. Для них пока нет событий аудита.

## Экспорт в SIEM <FeatureState feature="audit-siem-export" /> {#siem-export}

Semaphore Pro отправляет журнал аудита в SIEM по Syslog с TLS. Он хранит свою позицию в журнале для SIEM,
поэтому события, записанные, пока SIEM недоступен, отправляются, когда он снова доступен. Шаги см. в разделе
[Отправьте журнал аудита в SIEM](/admin-guide/audit-log-siem).
