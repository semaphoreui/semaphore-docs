# 🔐 Безопасность

## Введение {#introduction}

Безопасность — главный приоритет Semaphore UI. Автоматизируете ли вы критически важные инфраструктурные задачи или управляете доступом команды к чувствительным системам, Semaphore UI изначально спроектирован для надёжной и безопасной работы. В этом разделе описано, как Semaphore обеспечивает безопасность и что следует учитывать при развёртывании в production.

## Аутентификация и авторизация {#authentication--authorization}

Semaphore поддерживает безопасную аутентификацию и гибкие механизмы авторизации:

- **Способы входа:**
  - **Имя пользователя и пароль**<br />Способ по умолчанию, использующий учётные данные из базы данных Semaphore. Пароли никогда не хранятся в открытом виде; они хешируются алгоритмом Argon2id (см. [Хеширование паролей](#password-hashing)).

  - **LDAP**<br />Позволяет интегрироваться с корпоративными службами каталогов. Поддерживает фильтрацию пользователей и групп, а также защищённые соединения через LDAPS.

  - **OpenID Connect (OIDC)**<br />Обеспечивает единый вход с провайдерами идентификации, такими как Google, Azure AD или Keycloak. Поддерживает пользовательские claim-ы и сопоставление групп.

- **Двухфакторная аутентификация (2FA)**<br />Доступна двухфакторная аутентификация на основе TOTP, и её рекомендуется включить всем пользователям. Она включается для каждого пользователя и поддерживает необязательные коды восстановления. См. параметры конфигурации `mfa.totp.enabled` и `mfa.totp.allow_recovery`.

- **Управление доступом на основе ролей**<br />Пользователям можно назначать разные роли, например Admin, Maintainer или Viewer, ограничивая доступ в соответствии с зоной ответственности.

- **Управление сеансами**<br />Сеансы защищены безопасными HTTP-куками. Истечение срока сеанса и механизмы выхода сводят время экспозиции к минимуму.

### Хеширование паролей {#password-hashing}

:::info Начиная с v2.20
Хеширование паролей алгоритмом Argon2id доступно начиная с **Semaphore 2.20**. Более ранние версии используют bcrypt.
:::

Пароли локальных пользователей хешируются алгоритмом **Argon2id**, который [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) рекомендует для хранения паролей. Semaphore использует минимальные параметры стойкости, рекомендованные OWASP:

| Параметр | Значение |
|-----------|-------|
| Память | 19 МиБ (`m=19456`) |
| Итерации | 2 (`t=2`) |
| Параллелизм | 1 (`p=1`) |
| Соль | 16 случайных байт на пароль |
| Длина хеша | 32 байта |

Хеши хранятся в стандартном [формате строки PHC](https://github.com/P-H-C/phc-string-format/blob/master/phc-sf-spec.md), например `$argon2id$v=19$m=19456,t=2,p=1$<salt>$<hash>`, поэтому параметры, использованные для каждого хеша, записываются вместе с ним.

Это относится ко всем способам задания пароля: через веб-интерфейс, через API и через команды CLI `semaphore user add`, `semaphore user change-by-login` и `semaphore setup`.

**Обновление с версий до 2.20.** В выпусках до 2.20 пароли хешировались с помощью bcrypt. Отдельный шаг миграции не требуется:

- Существующие хеши bcrypt по-прежнему принимаются при входе, поэтому после обновления все пользователи продолжают работать.
- При первом успешном входе пароль прозрачно перехешируется алгоритмом Argon2id, а хеш bcrypt заменяется.
- Если в будущем выпуске параметры Argon2id в Semaphore будут усилены, хеши, созданные со старыми параметрами, обновятся тем же способом при следующем входе.

Поскольку перехеширование происходит только при входе, у пользователей, которые больше никогда не войдут, сохранится хеш bcrypt. Чтобы принудительно обновить такие учётные записи, сбросьте их пароль командой `semaphore user change-by-login --password ...` или через интерфейс администратора.

:::note
Коды восстановления для двухфакторной аутентификации не являются паролями пользователей и продолжают использовать bcrypt.
:::

## Секреты и учётные данные {#secrets--credentials}

Безопасное управление секретами — ключевая возможность:

- **Зашифрованное хранилище ключей**<br />Учётные данные и секретные переменные шифруются при хранении с помощью AES.

- **Изоляция окружения**<br />Секреты передаются заданиям только во время выполнения и не попадают напрямую в окружение контейнера.

- **SSH-ключи и токены**<br />Пользователи сами отвечают за загрузку корректных SSH-ключей и токенов. Они шифруются и используются только при выполнении задач.
- **Интеграция с HashiCorp Vault (Pro)**<br />Секреты могут храниться во внешнем экземпляре Vault. Хранилище выбирается для каждого секрета при его создании или изменении.

## Шифрование данных {#data-encryption}

Чувствительные данные хранятся в базе данных в зашифрованном виде. Чтобы включить шифрование ключей доступа, задайте в файле конфигурации параметр `access_key_encryption`. Его нужно сгенерировать командой:

```bash
head -c32 /dev/urandom | base64
```

## Выполнение недоверенного кода и playbook {#running-untrusted-code--playbooks}

Semaphore выполняет заданные пользователем playbook и команды, что может быть рискованно:

- **Изоляция выполнения**<br />По умолчанию задача — это обычный процесс на сервере Semaphore, с его файловой системой и сетевым доступом. Изоляция включается отдельно: передайте задачу [раннеру](/admin-guide/runners) с исполнителем `docker` или `k8s`, и для каждой задачи создаётся новый контейнер или Pod, который удаляется после завершения.

- **Минимальные привилегии**<br />В исполнителях Docker и Kubernetes вы сами выбираете образ, сеть и сервисный аккаунт, поэтому задача получает только то, что ей нужно.

- **Выполнение в chroot**<br />Semaphore может выполнять задачи внутри chroot-окружения, дополнительно изолируя среду выполнения от хост-системы.

- **Пользователь процесса задачи**<br />Задачи могут выполняться от имени выделенного системного пользователя без прав root (например, `semaphore`), чтобы снизить последствия возможных эксплойтов. Это необязательно и настраивается в соответствии с политиками системы.

## Безопасное развёртывание {#secure-deployment}

Чтобы развернуть Semaphore безопасно:

- **Используйте HTTPS**<br />
    Semaphore поддерживает HTTPS как через **встроенную поддержку TLS**, так и через **обратный прокси, например Nginx**. В production настоятельно рекомендуется включить HTTPS.

    Чтобы включить встроенную поддержку HTTPS, добавьте следующий блок в **config.json**:
    ```json
    {
        ...
        "tls": {
            "enabled": true,
            "cert_file": "/path/to/cert/example.com.cert",
            "key_file": "/path/to/key/example.com.key"
        }
        ...
    }
    ```

- **Работайте за межсетевым экраном**<br />Ограничьте доступ к интерфейсу Semaphore и базе данных только доверенными IP-адресами.

- **Безопасность базы данных**<br />Используйте надёжные пароли и разрешайте доступ к базе данных только для Semaphore.

## Обновления и управление патчами {#updates--patch-management}

Обновления безопасности публикуются регулярно:

- **Обновляйтесь**<br />Всегда используйте последний стабильный выпуск.

- **Список изменений**<br />Перед обновлением просматривайте изменения на GitHub.

- **Автоматические обновления**<br />При использовании Docker рассмотрите автоматизацию регулярных обновлений через конвейеры.

## Сообщение об уязвимостях {#reporting-vulnerabilities}

Нашли уязвимость? Помогите нам сохранить безопасность Semaphore:

- **Ответственное раскрытие**<br />Напишите нам на `security@semaphoreui.com`.
 
### Целевые сроки устранения уязвимостей {#vulnerability-resolution-targets}

Мы стремимся устранять полученные сообщения об уязвимостях в следующие сроки:

- Критические: в течение 30 дней
- Высокие: в течение 60 дней
- Средние: в течение 90 дней
- Низкие: по возможности, обычно в течение 180 дней

Для активно эксплуатируемых проблем, затрагивающих последние стабильные выпуски, могут выпускаться внеочередные патчи.

### Инструменты анализа безопасности кода {#code-security-tooling}

Мы используем CodeQL, Codacy, Snyk и Renovate для анализа кодовой базы и зависимостей, а также для автоматизации обновления зависимостей.
- **Без публичных эксплойтов**<br />Не публикуйте информацию об уязвимостях до выхода исправления.

- **Благодарности**<br />Исследователи безопасности по желанию могут быть упомянуты в примечаниях к выпуску.
